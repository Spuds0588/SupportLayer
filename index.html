Open source — drop-in diagnostics + live support

See exactly what your users see.
One script tag, no backend.

SupportLayer captures a one-frame snapshot, redacts the sensitive parts before capture, and POSTs the report straight to your webhook. When a report isn't enough, your support agent opens the same URL with role parameters and lands in a full-screen agent view: the customer's screen, the chat, and a floating dock of annotation tools — without a relay server, an S3 bucket, a third-party SDK, or a second app to maintain.

<script src="https://cdn.jsdelivr.net/gh/Spuds0588/SupportLayer@main/supportlayer.js" data-webhook="https://hooks.example.com/support" data-mode="chat" data-theme="#14b8a6"></script>

Drop-in configuration

Everything comes from data-* attributes on the script tag: mode, theme, blur rules, and a JSON field schema for the request form. Bad JSON falls back to a sane default instead of breaking your page.

Privacy before capture

Selector and regex redaction is applied to the DOM first, so the user physically sees blurred data in the share prompt and the snapshot. Every wrap and injected style is fully unwound when the session ends.

Async reports that land

mode="none" is a pure bug report: one 70%-quality JPEG frame downscaled to 1280px, plus diagnostics, POSTed with keepalive so it survives a navigation.

Live P2P, no relay

PeerJS opens a WebRTC data channel between the customer and the agent, who joins the customer's own page as a role. Your webhook only ever carries the link — media never touches a server you have to pay for.

Point, draw, hand over text

A floating tool dock sits over the shared screen, Zoom-style: Point spotlights, Click lands on the customer's real DOM, Draw sketches strokes that clear after 3s, and Type highlights a field and hands the text over for review instead of faking keystrokes.

Hardened by default

Honeypot field, 60-second sessionStorage rate limit, and a required isTrusted click. The widget UI lives in a Shadow DOM so no host stylesheet can reach it.

Integration

<!-- Drop-in: webhook, mode, theme,
     redaction rules, form schema -->
<script
    src="/supportlayer.js"
    data-webhook="https://api.domain.com/webhook"
    data-mode="chat"
    data-theme="#14b8a6"
    data-blur-selectors=".sensitive-data, .balance"
    data-blur-regex="(email|ssn)"
    data-fields='[{"name":"name","type":"text",
                  "label":"Your Name"},
                 {"name":"issue","type":"textarea",
                  "label":"Describe the bug"}]'
></script>

Modes: none (async report only), chat (data channel), audio (two-way voice), video (two-way voice and video). Media never touches a server — even the call is peer-to-peer — and the request form is generated from data-fields.

The mode is the developer's decision, fixed on the script tag. The user never sees a chat/audio/video switcher: the request panel simply becomes whichever one you configured, on both sides at once. Changing it is an edit to data-mode and a reload — not a user preference.

The agent role

Your webhook receives a URL that is the customer's page plus two parameters. Open it and the same script becomes the agent view — the request button is replaced by the customer's screen, the chat, and the tool dock.

// what live_session_url looks like
https://app.domain.com/checkout
   ?sl_role=agent&peer=sl-7f3a91

Nothing else is required — no separate portal, no extra deployment. Whatever auth protects /checkout protects the agent view too, so agents sign in like any other user. Options: data-live-base to point the link at a different page, sl_mode / sl_color to force a call mode or annotation colour.

Headless API

Set data-headless="true" to hide the floating button and drive everything from your own UI:

SupportLayer.requestHelp();
SupportLayer.getState();
  // IDLE · SENDING · WAITING · CONNECTED
SupportLayer.getSession();
SupportLayer.endSession();
SupportLayer.reset();

// Public events on window:
"supportlayer:state"
"supportlayer:webhook"

The supportlayer:webhook event is what powers the inspector on this page — integrators get the exact payload before it is sent.

Webhook payload

{
  "event_type": "support_request | support_update",
  "session_id": "uuid-1234-5678",
  "status":     "open | cancelled | completed",
  "mode":       "chat",
  "live_session_url": "/checkout?sl_role=agent&peer=sl-…",
  "snapshot":   "data:image/jpeg;base64,…",
  "user_data":  { "name": "Jane", "issue": "…" },
  "diagnostics": {
    "url": "https://client-site.com/checkout",
    "browser": "Mozilla/5.0 …",
    "viewport": "1920x1080",
    "timestamp": "2026-09-13T13:54:00Z",
    "window_geometry": { … }
  }
}

snapshot is null when the user declines the prompt or on support_update events. window_geometry lets the agent view map an entire-screen capture back onto the page.

Coordinate contract (read this before touching the overlay code)

Every coordinate that travels over the data channel is normalized to 0.0 – 1.0 of the customer's viewport. Pixels never cross the wire. The agent view normalizes against the rendered video geometry — computing the object-fit: contain letterbox offset first — and, when the customer shared an entire screen rather than a tab, offsets by the customer's reported window position and size. Get that wrong and clicks drift by exactly the letterbox margin, which is why it is spelled out here.

live_session_url is the customer's own page with ?sl_role=agent&peer=<id> glued on. The agent opens it (signed into your app like any other user) and the widget boots into the agent view instead of the request button — the customer is the callee, so that link is the only thing the agent needs. The customer's own tab meanwhile turns the request panel into the chat / audio / video call, both directions. Screen sharing stays opt-in: the widget posts a momentary snapshot at request time and never holds a capture stream open unless the user clicks Share my screen.
